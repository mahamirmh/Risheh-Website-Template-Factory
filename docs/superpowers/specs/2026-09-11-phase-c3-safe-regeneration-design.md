# Phase C3 — Safe Regeneration / Existing Project Update Engine

## Status
Approved architecture: **Hybrid Safe Regeneration + Three-Way Merge + Atomic Apply**

## 1. Goal
Extend the Factory so an existing project previously generated by C2 can be regenerated from a new validated `risheh.build-spec.v1` without silently deleting or overwriting legitimate manual edits.

C3 must preserve C2 create-mode, consume the same public Build Spec contract, generate the next deterministic project state, compare it with the previous generated baseline and the currently edited project, produce an explicit change plan, and apply only a safe result.

## 2. Contract Boundary
`risheh.build-spec.v1` remains the canonical public input contract.

C3 MUST NOT:
- introduce a new competing Build Spec;
- modify Phase B catalogs during regeneration;
- reinterpret missing business facts as fabricated content;
- require Git as a runtime dependency;
- silently overwrite user-modified files;
- delete a user-modified generated file without an explicit conflict;
- write outside the inspected project root.

C3 MAY introduce internal regeneration metadata under `.risheh/`. This metadata is runtime state, not a public input contract.

## 3. Core Model
C3 uses three versions of each generated file:

- **Base** — the exact file content produced by the last successful Factory generation/regeneration.
- **Current** — the file currently present in the user's project and potentially edited manually.
- **Next** — the deterministic file content C2 would generate from the new Build Spec and current Factory version.

The merge decision is derived from Base ↔ Current ↔ Next.

## 4. Pipeline

```text
Existing generated project
        +
New validated risheh.build-spec.v1
        ↓
Project Inspector
        ↓
Baseline Loader
        ↓
C2 Deterministic Next FilePlan
        ↓
Three-Way Diff
        ↓
Change Classifier
        ↓
Safe Merge Planner
        ↓
Staging Workspace
        ↓
Quality Pipeline
        ↓
Atomic Apply
        ↓
Updated project + regeneration report + new baseline
```

The original project remains unchanged until the staging result passes all required gates and contains no blocking conflicts.

## 5. Persistent Project State
Each generated project gains:

```text
.risheh/
├── state.json
├── baselines/
│   └── <generation-id>/
│       ├── manifest.json
│       └── files/
├── reports/
│   └── <regeneration-id>.json
└── conflicts/
    └── <regeneration-id>/
```

### `.risheh/state.json`
Tracks:
- schema: `risheh.regeneration-state.v1`;
- project ID;
- active generation ID;
- last successful Build Spec hash;
- last Factory/generator version;
- active baseline directory;
- regeneration sequence number.

### Baseline snapshot
The active baseline stores the content of every Factory-owned file from the last successful generation plus its SHA-256 hash and ownership metadata.

User-created files that were never Factory-owned are not copied into the baseline.

## 6. Ownership Model
Every file is classified as one of:

- `factory-owned` — emitted by C2 and tracked in provenance/baseline;
- `user-owned` — exists in the current project but has never been emitted by the Factory;
- `shared-modified` — Factory-owned file whose current hash differs from the baseline;
- `removed-current` — Factory-owned baseline file missing from current project;
- `new-next` — emitted by the next generation but absent from baseline;
- `removed-next` — present in baseline but no longer emitted by the next generation.

C3 never assumes ownership solely from path conventions.

## 7. Three-Way Classification Rules
For each Factory-owned path:

### Unchanged by user, changed by Factory
`Current == Base` and `Next != Base`
→ replace with Next automatically.

### Changed by user, unchanged by Factory
`Current != Base` and `Next == Base`
→ preserve Current automatically.

### Unchanged by both
`Current == Base` and `Next == Base`
→ no-op.

### Changed by both
`Current != Base` and `Next != Base`
→ attempt structural/text three-way merge.

- non-overlapping edits → auto-merge;
- overlapping edits → blocking conflict.

### File removed by next generation
If `Next` omits a baseline file:
- if `Current == Base` → safe delete;
- if `Current != Base` → conflict; preserve current file.

### File newly generated at an existing user-owned path
→ blocking path collision; never overwrite.

### Baseline file manually deleted
If baseline owns a path and Current is missing:
- if Next also removes it → no-op;
- if Next still requires it → conflict; C3 must not silently recreate over an intentional deletion.

## 8. Merge Strategy
C3 uses a deterministic merge adapter interface.

```ts
type MergeInput = { path: string; base: string; current: string; next: string };
type MergeResult =
  | { status: 'merged'; content: string; strategy: string }
  | { status: 'conflict'; hunks: ConflictHunk[] };
```

Initial adapters:
- text/Markdown/JSON/YAML/CSS/TS/TSX/JS/JSX → line-aware three-way merge;
- JSON provenance/state → schema-aware regeneration, never user-merged;
- binary files → no auto-merge in C3 v1; conflict if both sides changed.

C3 v1 does not attempt AST rewriting of arbitrary user code. This avoids unsafe semantic guesses. AST-aware merging can be a future extension.

## 9. Conflict Model
Conflicts are first-class results, not exceptions hidden in logs.

Each conflict records:
- path;
- conflict type;
- Base hash;
- Current hash;
- Next hash;
- reason;
- overlapping ranges when available;
- proposed Next copy location;
- whether the current project was modified (must remain false until apply).

Conflict artifacts are written under `.risheh/conflicts/<regeneration-id>/` only after user initiates regeneration; the existing source file remains untouched.

No Git-style conflict markers may be inserted into production source files automatically.

## 10. Regeneration Plan
Before changing any project file, C3 produces an immutable `RegenerationPlan` containing entries with statuses:

- `unchanged`
- `add`
- `update-factory`
- `preserve-user`
- `auto-merge`
- `delete-factory`
- `conflict`

Each entry records source hashes, resulting hash when known, ownership, and reason.

The plan itself is deterministic for identical Base, Current and Next inputs.

## 11. Staging and Atomic Apply
All non-conflicting operations are first materialized into a sibling staging directory, never directly into the active project.

Required flow:
1. inspect current project;
2. validate project identity/state;
3. generate Next FilePlan with C2;
4. compute regeneration plan;
5. stop before apply if blocking conflicts exist;
6. clone/copy the current project into staging while excluding transient directories (`node_modules`, `.next`, caches);
7. apply the regeneration plan only inside staging;
8. update generated provenance and pending baseline in staging;
9. run quality pipeline in staging;
10. if any quality gate fails, discard staging and leave original untouched;
11. if all gates pass, perform atomic directory swap/rename within the same filesystem;
12. retain rollback metadata until final state write succeeds.

If atomic rename is unavailable across filesystems, C3 must fail closed rather than fall back to partial in-place writes.

## 12. Rollback Safety
Before atomic apply, C3 creates a temporary rollback sibling of the active project.

If final rename/state update fails:
- restore the previous active directory;
- retain the regeneration report with failure stage;
- report failure without claiming success.

Rollback retention is bounded; successful old rollback directories are removed after final verification.

## 13. C2 Compatibility
C2 create-mode remains supported.

After a successful fresh C2 generation, C3 initialization records the first baseline under `.risheh/`.

Projects generated before C3 may be **adopted** only if:
- `risheh-generation.json` exists;
- project ID matches the new Build Spec;
- all provenance-listed files exist or deviations are explicitly classified;
- an initial baseline can be reconstructed safely from a clean deterministic regeneration matching recorded provenance hashes.

If safe baseline reconstruction is impossible, C3 refuses automatic regeneration and recommends creating a fresh generated project or explicit manual adoption.

## 14. Quality Gates
C3 must run both regeneration-specific and existing C2 gates.

Required regeneration gates:
1. valid existing C3 state or safe adoption;
2. project ID match;
3. baseline integrity;
4. no path traversal;
5. deterministic Next FilePlan;
6. no user-owned path overwrite;
7. no blocking conflicts;
8. regeneration result hash consistency;
9. state/provenance validity;
10. rollback path safety.

Then run C2 quality gates on staging:
- Build Spec validation;
- route existence/link checks;
- forbidden fake-data scan;
- placeholder scan;
- RTL structural check when applicable;
- TypeScript;
- ESLint;
- Next production build.

A regeneration is successful only when all applicable gates pass.

## 15. API Boundary
Recommended endpoint:

`POST /api/regenerate`

Input:
```json
{
  "projectId": "safe-project-id",
  "buildSpec": { "schema": "risheh.build-spec.v1" },
  "action": "preview" | "apply"
}
```

`preview` returns the regeneration plan and conflicts without altering the project.

`apply` recomputes the plan from current disk state before mutation; it must not trust a stale preview plan.

No API field may independently override routes, industry, Design DNA, or other Build Spec-owned values.

## 16. UI Integration
C1/C2 gains an Existing Project / Regenerate flow.

Primary states:
- Inspecting project;
- Baseline valid / adoption required / invalid project;
- Preview ready;
- Added / updated / preserved / merged / deleted / conflicted counts;
- Blocking conflicts;
- Validating staging project;
- Applying atomically;
- Complete;
- Failed with stage-specific diagnostics.

The UI must show change counts before apply and must never label a conflicted project as ready.

## 17. Regeneration Report
Every preview/apply produces structured evidence:

```ts
type RegenerationReport = {
  schema: 'risheh.regeneration-report.v1';
  regenerationId: string;
  projectId: string;
  previousGenerationId: string;
  nextGenerationId: string;
  status: 'preview' | 'blocked' | 'passed' | 'failed';
  counts: {
    unchanged: number;
    added: number;
    updated: number;
    preserved: number;
    merged: number;
    deleted: number;
    conflicts: number;
  };
  entries: RegenerationEntry[];
  quality: Record<string, boolean>;
  failure?: { stage: string; code: string; message: string };
};
```

Reports must not include secrets or environment variable values.

## 18. Security
- all project/workspace paths must resolve under configured regeneration root;
- reject symlink escapes when inspecting or applying files;
- never execute project-provided shell commands;
- quality commands are allowlisted by Factory runtime;
- ignore `.env*` contents during reports and snapshots;
- never copy secrets into baseline metadata;
- archive/report paths must be sanitized;
- project IDs remain subject to C2 naming safety.

## 19. Testing Strategy

### Unit tests
- ownership classification;
- Base/Current/Next decision matrix;
- safe delete rules;
- user-owned collision detection;
- line three-way merge non-overlap;
- overlap conflict detection;
- deterministic regeneration plan;
- state and baseline hashes;
- symlink/path traversal rejection.

### Integration tests
- regenerate untouched LTR project;
- preserve manual TSX component edit when Factory does not touch it;
- merge non-overlapping CSS changes;
- detect same-line TSX conflict;
- preserve user-added file;
- safely delete untouched obsolete generated route;
- block deletion of manually edited obsolete generated file;
- preserve manual deletion as conflict when Next still requires file;
- regenerate Persian RTL project;
- multiple sequential regenerations;
- failed Next build leaves original project byte-for-byte unchanged.

### Regression fixture journey
1. generate with C2;
2. initialize baseline;
3. manually modify selected generated files and add one user-owned file;
4. change Build Spec (route/content/DNA/pattern composition);
5. preview C3 plan;
6. apply non-conflicting update;
7. verify manual edits remain;
8. verify Factory changes appear;
9. verify quality gates pass;
10. verify new baseline becomes active.

## 20. Success Criteria
C3 is complete when:
- `risheh.build-spec.v1` remains unchanged;
- C2 fresh create-mode still passes existing tests;
- a previously generated project can be regenerated repeatedly;
- untouched generated files update automatically;
- manual edits are preserved when non-conflicting;
- overlapping edits produce explicit conflicts without touching original files;
- user-owned files are never overwritten;
- manually edited files are never silently deleted;
- staging failures leave the original project unchanged;
- successful updates are atomically applied;
- provenance, baseline and reports remain consistent after every success;
- representative LTR and Persian RTL projects pass regeneration and production build in CI;
- repeated identical preview inputs produce identical regeneration plans.

## 21. Out of Scope for C3 v1
- semantic AST merging of arbitrary application code;
- hosted multi-user regeneration jobs;
- GitHub PR creation for regenerated projects;
- database migrations;
- CMS content synchronization;
- deployment orchestration;
- automatic resolution of blocking conflicts;
- binary media merging.

These may be layered later without changing the C3 public Build Spec boundary.
